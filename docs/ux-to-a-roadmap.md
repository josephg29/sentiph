## Per-aspect path to A

### First Impression & Orientation — current 80 → A target 90
Loads instantly to a labeled console with a `?` affordance; the deduction is thin first-run onboarding plus first-paint correctness defects on smaller viewports. What blocks A: no initial app-load state (blank/half-render on slow backend), no `prefers-reduced-motion` opt-out for the perpetual canvas/edge animations, and the tablet band (768px) is a broken midpoint where the status-strip sparkline captions overlap/garble on first paint. - Blocking ids: **22, 42, 48, 53**

### Task Flow Clarity — current 84 → A target 90
The one-click spawn premise is sound and 404 recovers, but the live flow is broken in ways that create real dead ends. What blocks A: NEW AGENT does not reliably open a terminal (the pending-open effect no-ops), past-session rows and inactive nodes are dead clicks (navigate-to-conversation is unwired), the entire git lifecycle has no UI trigger, canvas nodes are keyboard-unreachable (the advertised Enter/Space is dead), and pan/zoom affordances are unsignposted. What blocks A: no way to find/jump to a specific terminal (no command palette/search), minimize destroys the panel with no restore tray, click-to-focus on an open node destructively closes it, batch/worktree spawn paths are code-only, and the mobile Agents view wastes ~45% of the screen with a ~180px terminal slit. ## Overall narrative
Sentiph is a strong, intentional power-tool whose B/84 is held back less by missing design than by **wiring gaps**: a remarkable amount of A-grade functionality already exists in code (`openAgentGitActions`, `loadError`, `backendLivenessStatus`, `isCreatingTerminal`, the connection-state machine, the orphaned zoom-control CSS) but is computed and then never rendered or never triggered, so the UI silently no-ops on exactly the moments — spawn failure, offline, reconnect, git — where an operator most needs feedback. The single biggest lever is a **toast/aria-live + error-boundary feedback layer**, because it simultaneously lifts Feedback & State and Error Recovery and is the destination for half a dozen already-existing-but-orphaned signals. The second lever is **fixing and surfacing the core agent loop** — make every NEW AGENT click open a focused terminal, give nodes identities and keyboard reachability, add a command palette and minimized dock, and put git on the header — which moves Task Flow, Friction, and Discoverability together. The third is **resilience and a11y hygiene** (error boundary, focus-trapped dialogs, connection/offline/failed-agent states) that takes Error Recovery from "happy-path only" to "graceful under failure." With the responsive-layout fixes rounding out First Impression on tablet/mobile, every aspect clears ~90 and the console reaches A — mostly by *rendering what it already knows* rather than building net-new logic.

# Completeness critique: what still blocks a clean A after the roadmap ships

I grounded this against the live `demo/refactor` tree, not just the roadmap prose. Note up front: several roadmap "net-new" items already exist in code (`app/toast.ts`, `components/ui/ToastHost.tsx` with a `aria-live="polite"` region, `AppErrorBoundary.tsx`, `ui/ConfirmationDialog.tsx`). So the toast/error-boundary/aria-live layer is partly *already built but unrouted* — which makes the roadmap's framing ("render what it already knows") correct, but also means the genuinely-missing UX classes below are the real residual gap to an A. The roadmap covers wiring and responsive fixes well; it under-covers the items below.

## 1. Backgrounded-agent completion is sound-only — no visual/OS channel (the single biggest miss)
`useTerminalCompletionNotification` fires a WebAudio beep on `processing → idle` and nothing else. There is no `Notification` API, no `document.title` badge, no favicon dot, no `setAppBadge`. For a tool whose whole premise is "babysit many agents in parallel," the defining job is telling you which agent needs you *when the tab is backgrounded or muted* — and that channel does not exist. The roadmap's #27 adds an aria-live announcement (good for SR users on the focused tab) but an aria-live region is silent to a backgrounded tab too. **Aspect: Feedback & State (and the named Discoverability intent).** *Fix:* on `processing → idle` and especially `waiting_for_permission`, fire a `Notification` (permission-gated, settings-toggle) + a `document.title` unread count + favicon dot, cleared on focus.

## 2. `waiting_for_permission` has no escalation path — the highest-stakes state is treated like any idle
The state union (`packages/core/.../agentRuntime.ts`) has `waiting_for_permission`, which is the one state that *blocks an agent indefinitely until the operator acts*. Today it renders only as a "PERMISSION" pill, with the same sound as a normal completion. The roadmap never singles it out. A console at A must make "agent N is blocked waiting on you" impossible to miss across tabs. **Aspect: Feedback & State / Friction.** *Fix:* a distinct persistent alert (not a 4s toast), a count in the nav, and a one-click "jump to the blocked agent."

## 3. No multi-agent at-a-glance summary — there is no aggregate status anywhere
`ActiveAgentsSidebar` is a pure layout shell (resizer + slots, zero counts), and nothing in the tree computes "3 processing / 2 idle / 1 needs-permission." The roadmap's command palette (#10) lets you *find* an agent if you know what you're looking for, but never gives the fleet overview. The intent note's own deduction ("hard to tell agents apart at a glance") is broader than naming — at 10+ agents you need a roll-up. **Aspect: Discoverability / Feedback & State.** *Fix:* a status-strip cluster or sidebar header with per-state counts (clickable to filter), derived from the existing `runtimeStateStore` snapshot.

## 4. No "completed/done" state — success is inferred, not modeled
The union is `idle | processing | waiting_for_permission | waiting_for_user`; a finished task collapses into the same `idle` as "spawned and never ran." So you cannot tell "this agent just finished its run" from "this agent is sitting idle," and the completion sound is a one-shot you can miss. Roadmap #12 adds a *failed* state but no *succeeded/finished* state. **Aspect: Feedback & State.** *Fix:* add a transient `completed` runtime state (or a per-agent "last finished at" badge) so finishes persist visually, not just as a beep.

## 5. Toast bus has no cap, no coalescing, no per-agent identity — it will become noise at scale
`toast.ts` pushes unbounded (`toasts = [...toasts, toast]`); `ToastHost` renders all of them; errors have `durationMs: 0` (never auto-dismiss). Route lifecycle events for 10 agents through it (roadmap #1) and a transient backend blip produces a wall of stacked, sticky error toasts that bury the screen — actively *worse* than the current silence. The roadmap treats "add toasts" as the fix without addressing volume. **Aspect: Feedback & State / Friction.** *Fix:* cap visible toasts (~3–5), coalesce by key (e.g. "5 spawn failures"), tag each with the agent name, and cap the lingering-error count.

## 6. Accessibility depth stops at the canvas/dialog surface — the terminal itself and live regions are under-specified
The roadmap does node focusability (#13), focus-trap dialogs (#8), and one aria-live region (#27). But: (a) xterm's canvas/WebGL renderer is opaque to screen readers and there's no documented SR strategy for the *primary work surface*; (b) `aria-live` is added in two unconnected places (the existing `ToastHost` polite region + the roadmap's new one) with no policy on assertive-vs-polite or duplicate announcements; (c) no color-contrast/`forced-colors` audit of the dark terminal chrome and the dashed/double state rings — which double as the *only* encoding for worktree/swarm/permission. **Aspect: Discoverability / Error Recovery.** *Fix:* enable xterm's screen-reader mode (`screenReaderMode`/accessibility buffer), define one assertive region for permission/failure and reserve polite for the rest, and add non-color redundancy + a `forced-colors` pass to the ring legend (#28).

## 7. Perceived-performance polish is essentially uncovered
The roadmap's only perf items are loading skeletons (#17). But the operator-facing perf cliffs are: (a) reconnect calls `terminal.reset()` (full clear) then replays history — a visible wipe-and-repaint flash on every reconnect; (b) the force simulation (`useForceSimulation`) plus per-node infinite edge animations run continuously with **no virtualization** anywhere — at 15–20 nodes the canvas will jank, and the roadmap's reduced-motion block (#26) helps motion-sensitivity but not throughput; (c) no debouncing/coalescing strategy for high-frequency PTY output is mentioned. **Aspect: Friction / First Impression.** *Fix:* replay into an offscreen buffer and swap (no flash); pause the force sim once settled and cap/virtualize node animations; throttle output writes.

## 8. Mobile/touch parity is patched, not designed — terminal input on touch is unaddressed
The roadmap fixes mobile *layout* (#21, #22, #24) and pinch-zoom of the canvas (#23), but never addresses *operating a terminal on touch*: there is no on-screen affordance for Esc/Ctrl/Tab/arrows, and a real on-screen keyboard will cover the ~25-row terminal #21 just fought to create. A console that "reaches A" on mobile must let you actually type into an agent. This is parity, not polish. **Aspect: Friction / Task Flow Clarity.** *Fix:* a compact modifier-key bar (Esc/Ctrl/Tab/↑↓) above the terminal and visualViewport-aware resize so the keyboard doesn't occlude the work surface — or an explicit, signposted "desktop-recommended" stance so mobile isn't a half-built dead end.

## 9. Mis-prioritization: worktree dialog ID-retyping (#33) and worktree status-error surfacing (#23) are ranked far below their real friction
Two genuinely silent-failure / high-annoyance items sit at #31 and #33 (near the bottom), below cosmetic items like the glyph legend (#28) and status-strip label clarity (#29). For an operator using worktree agents, retyping a non-memorable full terminal ID to clean up (#15/#33) and worktrees whose git/PR fetches fail silently (#23/#31) are everyday friction on the *advanced* path the intent note cares most about. **Aspect: Friction / Feedback & State.** *Fix:* pull both above the cosmetic Discoverability cluster.

## 10. No connection-state recovery for the *control-plane* sockets (events + liveness), only the per-terminal PTY socket
The roadmap's #11/#12 cover the per-terminal WebSocket and PTY-exhaustion. But `useTerminalEventsSocket` (the global agent-state feed) and `useBackendLivenessPolling` are separate channels: if the *events* socket dies, every agent's state silently freezes at its last value while the per-terminal terminals still look connected — a subtler, more dangerous "everything looks fine but is stale" failure than a single dead PTY. The roadmap surfaces offline (#6) but not "state feed stale." **Aspect: Error Recovery / Feedback & State.** *Fix:* a "live/stale" indicator driven by the events-socket heartbeat, distinct from the backend-liveness pill, so frozen-but-rendered agent state is visible.

---

**Net:** the roadmap will clear the *wiring* and *responsive* deductions the rubric names, but three whole classes keep it off a clean A: (1) **cross-tab/OS notification for finishes and especially permission-blocks** (items 1–2, 4), (2) **at-scale legibility** — fleet roll-up, toast volume control, node/output virtualization (items 3, 5, 7), and (3) **depth on the two surfaces the rubric leans on hardest — the terminal itself (a11y + touch input, items 6, 8) and the multi-socket control plane (item 10)**. Items 1, 3, and 5 are the highest-leverage additions; item 9 is a straight reprioritization.
